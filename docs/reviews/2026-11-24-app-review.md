# 2026-11-24 앱 전체 리뷰와 후속 작업

검토 기준은 `main`의 `6455c56`과 로컬 주요 설계 문서다. iOS 1.0, 동시 사용 기기 두 대, 기기별 수만 장 사진첩을 가정했다. Apple 로그인과 토큰 철회는 개발자 계정 신청이 진행 중이므로 이 작업 범위에서 제외한다. Android 출시 준비와 운영 환경 배포는 후속 검증에 해당한다.

## 리뷰와 구현 계획

| 번호 | 발견 사항 | 완료 기준 |
| --- | --- | --- |
| 1 | 기기의 사진 권한을 끄면 기존 비교 승인 철회도 막힌다 | 서버 승인 목록을 사진 권한 없이 열고 항목을 철회할 수 있다. 새 승인은 읽을 수 있는 로컬 기록만 사용한다. |
| 2 | 사진 조회 실패 또는 로딩 때 여행 삭제 확인창에 0장이 표시된다 | 사진 조회가 성공해야 삭제를 시작하고, 확인 이후 장수가 달라지면 다시 확인한다. |
| 3 | 이미 삭제한 자동 여행에 진행 중이던 사진 업로드가 붙을 수 있다 | 서버가 확인 상태 및 여행 삭제와의 동시성을 검사한다. 상세는 삭제된 여행을 닫힌 상태로 표시한다. |
| 4 | 전체 사진첩에서 고른 기준일 이전 사진의 촬영 정보가 서버로 갈 수 있다 | 앱과 서버 모두 기준일을 검사한다. 위치 판단은 기기 안에서 한다. |
| 5 | 사진·댓글 신고 경로와 공개 처리방침 정보가 필요하다 | 사진·글의 신고는 기존 열람 범위에서 접수하고, 운영 담당자만 처리할 수 있게 한다. 운영자명·연락처·시행일은 확인된 값만 쓴다. |
| 6 | 커플 사진 1,000장 한도와 사용량 표시가 빠져 있다 | 동시 등록까지 서버가 한도를 강제한다. 설정에서 사용량을 읽고 업로드 한도 오류를 구분한다. |
| 7 | 오류 수집 필터와 개인정보 보고가 실제 SDK 동작 범위와 다르다 | 허용된 오류 필드만 보내고 자동 세션과 별도 전송 경로를 제어한다. 보고서와 처리방침에 같은 범위를 쓴다. |
| 8 | README가 현재 일일 정리 예약과 다른 키 설정을 안내한다 | 기존 마이그레이션이 등록한 작업과 별도 Vault 토큰을 기준으로 안내한다. |
| 9 | 증분 스캔 조회 구간이 겹칠 수 있다 | 스캔 시작을 상한으로 잡고 이전 체크포인트와의 경계에 있는 사진을 한 번만 집계한다. |
| 10 | 상대 탈퇴 유예 중 지난 기록 사진을 보존할 경로가 없다 | 지난 기록을 읽을 수 있는 사용자가 사진 한 장을 사진첩에 저장할 수 있다. |
| 11 | 작은 지도 조각과 사진 격자의 접근성이 부족하다 | 목록에서 충분한 탭 크기로 조각을 고르고, 스크린 리더가 사진 항목을 구분한다. |

작업 단위는 스캔·승인, 여행 삭제, 사진 업로드와 한도, 진단·배포 문서, 신고·사진 보존, 지도 접근성이다. 각 단위에서 실패하는 회귀 테스트를 먼저 확인한 뒤 가장 작은 변경을 적용한다. 사진 삭제와 등록, 신고, 사진 메타데이터는 서버 테스트도 포함한다.

## 검증 기준

- `flutter test`, `dart analyze`, `supabase test db --local`, 등장하는 동시성 테스트를 통과시킨다.
- 정리 함수 Node 테스트와 지도 원본 기준 229조각·본토 228개 탭 판정·보완 인접 590개를 확인한다.
- 리뷰 시점에 앱 테스트 270개, Supabase 통합 37개, DB 검증 277개, 정리 함수 14개가 통과했다.
- iOS 실기기의 iCloud, 사진첩 저장 권한, VoiceOver, 운영 환경의 신고 대응과 일일 정리 실행은 출시 리허설에서 확인한다.
